## 4. ბექენდის არქიტექტურა

### 4.1 სტეკი

ჩემი პროექტი ფრონტენდზეა ორიენტირებული, ამიტომ ბექენდისთვის ავირჩიე უმარტივესი ვარიანტი:

- **json-server** — `db.json` ფაილიდან ავტომატურად ქმნის REST API-ს (GET, POST, PATCH, DELETE);
- **json-server-auth** — json-server-ს ამატებს რეგისტრაციას, შესვლას და JWT ტოკენებს.

ასე სერვერის კოდის წერა თითქმის არ მჭირდება, მონაცემები კი რეალურ API-ს ჰგავს. მომავალში ნამდვილ ბექენდზე (მაგ. Node.js + Express) გადასვლისას ფრონტენდში მხოლოდ მისამართის შეცვლა იქნება საჭირო.

### 4.2 მონაცემთა ბაზის სტრუქტურა (`db.json`)

| კოლექცია | რა ინახება |
|---|---|
| `users` | თანამშრომლები (სახელი, ელ. ფოსტა, პაროლი, როლი) |
| `items` | ნივთები/მარაგები |
| `vendors` | მომწოდებლები |
| `orders` | შესყიდვის შეკვეთები |
| `shipments` | შემოსული ტვირთები |
| `deliveries` | მიწოდებები |

### 4.3 ავტორიზაცია — რატომ JWT

ავირჩიე **JWT (JSON Web Token)**.

**როგორ მუშაობს:**
1. მომხმარებელი აგზავნის ელ. ფოსტას და პაროლს `POST /login`-ზე;
2. სერვერი ამოწმებს და აბრუნებს ტოკენს (`accessToken`);
3. ფრონტენდი ინახავს ტოკენს `localStorage`-ში;
4. ყოველ შემდეგ მოთხოვნას ტოკენი თან ახლავს ჰედერში: `Authorization: Bearer <token>`;
5. გასვლისას (Logout) ტოკენი იშლება.

**რატომ JWT და არა Sessions/Cookies:**
- სერვერს არ სჭირდება სესიების შენახვა — ტოკენშივე წერია, ვინ არის მომხმარებელი;
- json-server-auth-ს JWT უკვე აქვს ჩაშენებული;
- React-ში მარტივია: ტოკენს ვინახავ, ვამატებ მოთხოვნებს და ვამოწმებ, შესულია თუ არა მომხმარებელი;
- ყველაზე გავრცელებული მიდგომაა React აპლიკაციებში.

**როლები:** მომხმარებლის ობიექტში არის ველი `role` (`manager`, `purchasing`, `operator`, `logistics`). შესვლის შემდეგ ფრონტენდი როლის მიხედვით აჩვენებს შესაბამის გვერდებს.

## 5. API ენდფოინთები

**Base URL:** `http://localhost:3000`

### 5.1 სრული სია

| მეთოდი | URL | აღწერა | ვის შეუძლია |
|---|---|---|---|
| POST | `/login` | სისტემაში შესვლა | ყველას |
| GET | `/users` | თანამშრომლების სია | მენეჯერი |
| POST | `/users` | ახალი თანამშრომლის დამატება | მენეჯერი |
| GET | `/items` | ნივთების სია (ძებნა, ფილტრი, გვერდები) | ყველა |
| GET | `/items/:id` | ერთი ნივთის დეტალები | ყველა |
| PATCH | `/items/:id` | რაოდენობის შეცვლა (კორექტირება) | მენეჯერი, ოპერატორი |
| GET | `/vendors` | მომწოდებლების სია | მენეჯერი, შესყიდვები |
| POST | `/vendors` | მომწოდებლის დამატება | შესყიდვები |
| GET | `/orders` | შესყიდვის შეკვეთები | მენეჯერი, შესყიდვები |
| POST | `/orders` | ახალი შეკვეთის შექმნა | შესყიდვები |
| PATCH | `/orders/:id` | შეკვეთის დამტკიცება / უარყოფა | მენეჯერი |
| GET | `/shipments/:id` | ტვირთის ნახვა მისაღებად | მენეჯერი, ოპერატორი |
| PATCH | `/shipments/:id` | მიღებული რაოდენობების შენახვა | მენეჯერი, ოპერატორი |
| GET | `/deliveries` | მიწოდებების სია | მენეჯერი, ლოჯისტიკა |
| PATCH | `/deliveries/:id` | მიწოდების სტატუსის შეცვლა | ლოჯისტიკა |

**ძებნა და ფილტრი json-server-ში:**
- `GET /items?category=Electronics` — ფილტრი კატეგორიით;
- `GET /items?_sort=name&_order=asc` — სორტირება;
- `GET /items?_page=1&_limit=10` — პაგინაცია;
- `GET /items?q=laptop` — ძებნა.

### 5.2 ძირითადი მარშრუტები მაგალითებით

#### 1) შესვლა — `POST /login`

მოთხოვნა:
```json
{
  "email": "manager@wms.ge",
  "password": "123456"
}
```

პასუხი `200 OK`:
```json
{
  "accessToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "user": {
    "id": 1,
    "name": "გიორგი ბერიძე",
    "email": "manager@wms.ge",
    "role": "manager"
  }
}
```

შეცდომა `400 Bad Request`:
```json
"Incorrect password"
```

### 5.3 შეცდომების კოდები

| კოდი | როდის |
|---|---|
| `200` | წარმატებული მოთხოვნა |
| `201` | ახალი ჩანაწერი შეიქმნა |
| `400` | არასწორი მონაცემები (მაგ. არასწორი პაროლი) |
| `401` | ტოკენი არ არის ან ვადა გაუვიდა — საჭიროა ხელახლა შესვლა |
| `403` | როლს არ აქვს ამ მოქმედების უფლება |
| `404` | ჩანაწერი ვერ მოიძებნა |
